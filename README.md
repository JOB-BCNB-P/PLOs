# ระบบสารสนเทศเพื่อการประเมินผลลัพธ์การเรียนรู้ระดับหลักสูตร (PLOs)

> **ทุกคำตัดสินมีเส้นทางกลับสู่คะแนนดิบ** — เว็บแอปสำหรับติดตามผลลัพธ์การเรียนรู้รายบุคคล สรุประดับชั้นปี รุ่น และหลักสูตร โดยแสดงหลักฐาน กฎการตัดสิน และร่องรอยการเปลี่ยนแปลงอย่างตรวจสอบได้

โครงการนี้เป็น **React + TypeScript + Vite** ฝั่งผู้ใช้ เชื่อมต่อฐานข้อมูลและการยืนยันตัวตนผ่าน **Supabase** พร้อม workflow สำหรับตรวจสอบและเผยแพร่แบบ static ไปยัง GitHub Pages ออกแบบตามแนวคิด *Clinical Aurora* เพื่อให้ข้อมูลการประเมินที่ซับซ้อนอ่านได้อย่างเป็นระบบบนเดสก์ท็อปและอุปกรณ์เคลื่อนที่

| พื้นที่ | สิ่งที่จัดเตรียมไว้ |
|---|---|
| หน้าจอ | เข้าสู่ระบบ, ภาพรวม PLO, รายบุคคล, ชั้นปี, รุ่น, หลักสูตร และสิทธิ์ผู้ใช้ |
| ฟีเจอร์ใหม่ | ฟอร์มบันทึกคะแนนพร้อมอัปโหลดหลักฐาน, กราฟผลสัมฤทธิ์รายชั้นปี, Export PDF/Excel |
| กติกาผลสัมฤทธิ์ | ประเมินเฉพาะ M/P, เกณฑ์ 3.51, รอผลเมื่อคะแนนไม่ครบ, ใช้ผลซ่อมเสริมล่าสุด และผ่านทุก sub-PLO |
| ข้อมูล | Schema, RLS, audit log, storage หลักฐานส่วนตัว และ migration ที่ทำซ้ำได้ |
| ความปลอดภัย | Google OAuth 2.0, บทบาทผู้ใช้, least privilege, hash เลขบัตรประชาชน และ RLS |
| การเผยแพร่ | GitHub Actions ตรวจ type/test/build แล้ว deploy ไปยัง GitHub Pages |

## เริ่มต้นอย่างรวดเร็ว

ติดตั้ง Node.js 22 และ pnpm 10 จากนั้นกรอกค่า Supabase ใน `.env.local` และเริ่มระบบตามคำสั่งต่อไปนี้:

```bash
git clone https://github.com/JOB-BCNB-P/PLOs.git
cd PLOs
cp .env.example .env.local
pnpm install
pnpm dev
```

## ฟีเจอร์ข้อมูลจริงและการใช้งานล่าสุด

Dashboard รองรับการค้นหานักศึกษาตามรหัสหรือชื่อ โดยค้นจากตาราง `students` ใน Supabase และจำกัดผลลัพธ์ 20 รายการเพื่อให้ตอบสนองเร็ว ผู้ใช้ที่เลือกจากผลค้นหาจะถูกนำไปยัง Student View พร้อมประวัติหลักฐานของนักศึกษารายนั้น

Student View รองรับการดู metadata หลักฐาน เปิดไฟล์ผ่าน signed URL อายุสั้น ดาวน์โหลด และลบไฟล์ตาม storage policy และ RLS ของผู้ใช้ การบันทึกคะแนนตรวจ session, สิทธิ์, duplicate attempt และบันทึก metadata ด้วย RPC ที่ใช้ transaction เดียวเมื่อมีไฟล์

ข้อมูลโครงสร้างหลักสูตรในระบบเป็น **ข้อมูลจริงจากเอกสารฉบับอนุมัติ** แล้ว ได้แก่ PLO 10 ข้อ, sub-PLO 24 ข้อ (ตารางที่ 19 ของเล่มหลักสูตร), รายวิชา 53 รายวิชา (124 หน่วยกิต) และ Curriculum Mapping ระดับ sub-PLO จำนวน 260 จุด (I=26, R=106, M=66, P=62) โดยยึดรหัสวิชาตามเล่มหลักสูตร `0101300xxx` และเก็บรหัสในไฟล์ Curriculum Mapping `0118300xxx` ไว้ที่ `courses.course_code_alt` เพื่อให้ค้นหาและนำเข้าได้ทั้งสองแบบ รายละเอียดการตรวจทาน ข้อสังเกตที่ควรเสนอคณะกรรมการหลักสูตร และช่องว่างที่พบ (sub-PLO 7.2 ยังไม่มีรายวิชารับผิดชอบ) อยู่ใน `docs/09_real_data_load_report.md`

โหมด `?demo=1` ใช้สำหรับดูรูปแบบหน้าจอเท่านั้น การค้นหา, บันทึกคะแนน และประวัติหลักฐานแบบ production ต้องใช้งานผ่าน session ที่ผ่าน Supabase Authentication และ policy ที่เหมาะสม


## ฟอร์ม CSV และการนำเข้าข้อมูล

ข้อมูลที่ต้องกรอกเอง ได้แก่ รายชื่อนักศึกษา ผู้สอน/บุคลากรและสิทธิ์ ผู้สอนประจำรายวิชา อาจารย์ที่ปรึกษา และการลงทะเบียนเรียน มีฟอร์ม CSV พร้อมคำอธิบายทีละคอลัมน์อยู่ที่ `docs/templates/` และดาวน์โหลดได้จากหน้า **ผู้ดูแลระบบ → นำเข้าข้อมูล CSV**

ฟอร์มบันทึกเป็น UTF-8 with BOM เปิดใน Excel แล้วภาษาไทยไม่เพี้ยน บรรทัดที่ขึ้นต้นด้วย `#` เป็นคำอธิบายและตัวอย่าง ระบบจะข้ามให้อัตโนมัติ

การนำเข้าทุกประเภททำผ่าน RPC `import_csv_rows` ในทรานแซกชันเดียว ตรวจสิทธิ์ role `admin` resolve คีย์อ้างอิงให้เอง (รหัสนักศึกษา, อีเมล, รหัสวิชา, รุ่นหลักสูตร) และบันทึก `audit_log` ทุกครั้ง ถ้ามีแถวใดผิดจะไม่บันทึกทั้งไฟล์

เลขประจำตัวประชาชนกรอกเป็นเลข 13 หลักได้ตามปกติในคอลัมน์ `national_id` ระบบแปลงเป็น HMAC-SHA256 ด้วย pepper ที่เก็บในตาราง `app_secrets` (อ่านผ่านแอปไม่ได้) ก่อนบันทึก และไม่เก็บเลขดิบไว้ที่ใด

## ลงทะเบียนอีเมลล่วงหน้า

อีเมลของอาจารย์และนักศึกษาบันทึกไว้ล่วงหน้าได้ก่อนที่เจ้าตัวจะเข้าสู่ระบบครั้งแรก บุคลากรที่ยังไม่มีบัญชีจะถูกเก็บในตาราง `pending_staff` พร้อม role และสิทธิ์ที่ตั้งไว้ ส่วนนักศึกษาเก็บที่ `students.email` เมื่อผู้ใช้ล็อกอินด้วย Google ครั้งแรก trigger `handle_new_user` จะจับคู่อีเมลแล้วให้สิทธิ์หรือผูก `student_access` อัตโนมัติ สำหรับบัญชีที่ล็อกอินไปก่อนแล้ว เรียก RPC `apply_pending_staff()` เพื่อใช้รายชื่อย้อนหลังได้ (การนำเข้า CSV เรียกให้อยู่แล้วในตัว)

## การเข้าสู่ระบบ

หน้า Login มีปุ่มเลือกประเภทผู้ใช้ บุคลากร/อาจารย์ กับ นักศึกษา เพื่อบอกขั้นตอนให้ตรงกลุ่ม แต่ทั้งสองทางเข้าสู่ระบบด้วยอีเมลผ่าน Google เหมือนกัน และไม่มีการกรอกเลขบัตรประชาชนในหน้าจออีกต่อไป สิทธิ์มาจากรายชื่อที่ลงทะเบียนไว้ล่วงหน้า (`pending_staff` สำหรับบุคลากร, `students.email` สำหรับนักศึกษา) ไม่ใช่จากหน้าจอที่ผู้ใช้เลือก

เมนูถูกกรองตามบทบาท: นักศึกษาเห็นเฉพาะผลของตนเองและโครงสร้างหลักสูตร บุคลากรเห็นภาพรวมทั้งหมด และเมนูผู้ดูแลเปิดให้เฉพาะ role `admin` โดยขอบเขตความปลอดภัยจริงยังบังคับด้วย RLS ที่ฝั่งฐานข้อมูล

## หนึ่งคนหลายบทบาท

`user_roles` มีคีย์หลักเป็น `(user_id, role)` ผู้ใช้หนึ่งคนจึงถือได้หลายบทบาทพร้อมกัน เช่น `executive` + `program_chair` + `lecturer` สิทธิ์ที่ได้เป็นสหภาพของทุกบทบาท และเมนูที่เห็นคือสหภาพของทุกบทบาทเช่นกัน (`viewsForRoles`) ส่วนป้ายบนหน้าจอแสดงบทบาทกว้างที่สุดพร้อมตัวเลข +N

ในฟอร์ม `staff.csv` ใส่หลายบทบาทในช่อง `role` ช่องเดียวคั่นด้วย `|` การนำเข้าจะแทนที่ชุดบทบาทเดิมทั้งหมด

แยกให้ชัดระหว่าง **บทบาท** (ระดับสิทธิ์) กับ **การมอบหมาย** (ขอบเขตข้อมูล): คำถามว่าเห็นนักศึกษาคนไหนหรือวิชาไหน ตอบโดย `class_advisor_assignments` และ `course_instructors` ผ่านฟังก์ชัน `can_view_student` และ `can_manage_course` ไม่ใช่โดยบทบาท
